> **Core Files**:  
> - [`scripts/build-vrm/workflow.mjs`](../scripts/build-vrm/workflow.mjs) (End-to-end pipeline orchestrator)  
> - [`scripts/build-vrm/build_vrmbase.mjs`](../scripts/build-vrm/build_vrmbase.mjs) (Generates `.vrmbase` base model archive)

> - [`scripts/build-vrm/compress_vrm.mjs`](../scripts/build-vrm/compress_vrm.mjs) (oxipng-based offline texture recompression)

---

## 1. Why an Offline Packaging Pipeline?

- **The Problem**: VRM models directly exported from VRoid Studio weigh 18MB ~ 25MB each. Distributing 5 complete outfits would demand over **100MB of network download**, resulting in unacceptable cold starts and poor outfit-swap latency.
- **The Solution**:
  - **Base Model (`.vrmbase`)**: Contains only the naked base mesh, head, armature, and shared materials (~5.9MB);
  - **Outfit Addon (`.vrmaddon`)**: Extracts delta binary patches via `bsdiff` against the base (containing only outfit meshes, clothes textures, and delta JSON metadata), reducing package size to 0.7MB ~ 4.7MB (**~65% overall payload reduction**);
  - **Client-Side Synthesis**: Assembles complete VRM binary files inside a Dedicated Web Worker using WebAssembly `bspatch` with zero-copy transfer.

## 3. Workflow Execution

### 3.1 CLI Commands
```bash
# Auto-detect single base model in .vroid/base/ and run full pipeline
node scripts/build-vrm/workflow.mjs

# Or specify a custom base model name explicitly
node scripts/build-vrm/workflow.mjs xiaochun_base
```

### 3.2 Pipeline Stages
1. **Stage 1 (Texture Compression)**: Calls `compress_vrm.mjs`, unpacks embedded PNG textures from glTF buffers, and runs multi-threaded `oxipng` lossless optimization;
2. **Stage 2 (Base Packaging)**: Calls `build_vrmbase.mjs`, stripping redundant meshes and bundling `.vrmbase`;
3. **Stage 3 (Addon Packaging)**: Calls `build_vrmaddon.mjs`, generating `.vrmaddon` diff packages via `bsdiff` comparison against the base model;
4. **Stage 4 (Config Verification)**: Automatically verifies `APP_CONFIG.model.addons` in `src/config.ts`:
   - Computes SHA-256 hashes of generated artifacts;
   - Emits structured warnings if config declarations are out of sync with filesystem outputs.

## 4. Engineering Guarantees: Determinism & Idempotency

1. **Fixed Zip Timestamps (Deterministic Builds)**:
   - Standard zip formats record current system timestamps, producing divergent SHA-256 hashes for identical source files;
   - The build toolchain pins all internal file `mtime` values to UTC `2026-01-01 00:00:00`, guaranteeing pure functional build reproducibility.
2. **SHA-256 Byte-Level Skip (Idempotent Disk I/O)**:
   - Evaluates memory-generated byte buffers against target disk files via SHA-256;
   - Skips disk writes when hashes match, eliminating false Vite HMR triggers and spurious Git diff churn.

## 5. Runtime Consumption: vrmWorker & 2-Tier Caching

Generated `.vrmbase` and `.vrmaddon` files are consumed by [`src/core/vrmWorker.ts`](../src/core/vrmWorker.ts) at runtime:
- The worker executes `fflate` decompression, WASM `bspatch` reassembly, and glTF 4-byte boundary padding;
- Stores composed assets in IndexedDB L2 via [`src/lib/idb-vrm-cache.ts`](../src/lib/idb-vrm-cache.ts);
- Communicates with the main thread via `Transferable ArrayBuffer` zero-copy IPC;
- Full lifecycle details and zero-frame T-pose elimination are documented in [`docs/OUTFIT_SWAP.md`](OUTFIT_SWAP.md) and [`docs/VRM_ENGINE_AND_WORKER.md`](VRM_ENGINE_AND_WORKER.md).
